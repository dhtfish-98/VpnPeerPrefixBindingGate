# Hosted Linux verification boundary

The GitHub workflow checks every pull request with Go race tests, vet, and Linux AMD64/ARM64 builds. The real-kernel job runs only on a `push` to `main` or a `v*` tag. There is no `pull_request_target` or manual ref-selection trigger. Both jobs request only `contents: read`; checkout does not persist its credential. The workflow's ref filter does **not** establish branch or tag protection: who can push `main` or create `v*` tags must be checked separately in repository rules before treating the kernel job as a trusted publication gate. A pull request can also change its own workflow content, so this file is not an enforcement boundary against someone able to alter CI configuration.

The kernel job uses an Ubuntu 24.04 hosted VM, installs distro `busybox`, `wireguard-tools`, `iproute2`, `kmod`, and `util-linux`, and builds `wirelab` into `Build/ci`. It starts the same experiment matrix as the local Alpine VM through `sudo unshare --mount --net --pid --fork --mount-proc`. The new network namespace has no external interface; two further peer network namespaces, real kernel WireGuard/veth/TUN devices, the intentionally weak gateway, and the separate guarded gateway are exercised there. The entry process mounts a private 0700 tmpfs at `/tmp`; test keys are 0600 and stay there. The PID namespace exits with the experiment, killing its peer holders and discarding the private mount. The module loader may load host kernel modules, so this job is limited to trusted pushes. The runner must already expose `/dev/net/tun`; the job refuses to create a device node on the host.

After the real WireGuard comparison, the experiment disables IPv4 reverse-path filtering for its synthetic TUN receivers inside the disposable network namespace. The deliberately injected packets carry source addresses whose return routes point to `wg0`, so a strict runner default would discard them at `weak0` and `guard0` before the UDP listeners could measure either gateway. The script checks the namespace's `all`, `default`, `weak0`, and `guard0` values and emits two required receipt markers. It does not change the host namespace or WireGuard's earlier spoof/replay comparison. This fixture setting is explicit because it affects only the synthetic gateway experiment, not a production VPN recommendation.

The machine receipt is produced under `Build/ci/machine-receipt.json` even when setup or runtime fails after checkout. A pre-run placeholder reports `INFRA_ERROR` with `hosted_execution_pending`, and the launcher replaces it when it runs. The receipt distinguishes the checked-out Git commit from the GitHub event SHA, which can refer to a tag object. It includes run identifiers, kernel/image and installed package versions, raw-log hash and length, exit/stage, required marker counts, and independent checks of nine receiver deliveries and six guard decisions. Only this allow-listed JSON is uploaded. Raw setup/runtime logs, generated private keys, and packet bytes remain local to the ephemeral runner and are not uploaded. Missing namespace/WireGuard capability yields `OPEN_HOSTED_RUNTIME`; package/build setup failure yields `INFRA_ERROR`; a failure after the tunnel is configured yields `TEST_FAIL`. Every non-`PASS` state exits nonzero. A green build job or an uploaded receipt does not substitute for a `PASS` real-kernel receipt.

The same-root peer processes share a mount namespace and can read one another's root-owned keys. This experiment therefore does not prove containment of a malicious peer with filesystem access. It tests packet-policy behavior under non-leaked test keys. WireGuard's own spoof and replay rejection is a comparator; this project neither implements nor patches WireGuard. The independent gate acts only before the synthetic tunnel writes a packet to TUN. A local VM PASS does not establish a hosted Ubuntu run: its result remains OPEN until the exact public run's job result and downloaded receipt are independently checked.

The first public hosted run on commit `625c4568d73346ac44f8703d5bb1835060375de9` failed after the kernel experiment started. Its downloaded machine receipt and the bounded local diagnosis are recorded in [HOSTED_FAILURE_37407758390.md](HOSTED_FAILURE_37407758390.md). The failure remains historical evidence; only a later exact-commit hosted job and receipt can establish that the fixture change works on Ubuntu.
